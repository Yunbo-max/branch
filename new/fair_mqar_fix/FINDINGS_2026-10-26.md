## 0. 一句话结论

几个训练任务**并非都因为显存(OOM)停的**,是三种不同原因混合:

1. **CUDA OOM**:`full` / `fork` v1/v2、`bench-single-vs-addable` —— full-covariance + `max_states=64` 时显存超 80GB。
2. **磁盘写失败(checkpoint 保存)**:MARCH(step 290k)、`m64-v2`(step 70k)。
3. **argparse 代码 bug**:`m64-v1`(13 秒就挂,`--grad-checkpoint` 重复定义)。

正常跑完(时间预算)的只有 `m64-fix`(81.6k 步)、`branch_mqar`、`16k pilot`。

## 2. 磁盘写失败(不是内存)

MARCH 和 `m64-v2` 都是**同一个磁盘错误**,发生在写 checkpoint 时:

```
RuntimeError: PytorchStreamWriter failed writing file data/0: file write failed
RuntimeError: unexpected pos 19456 vs 19350
```

- MARCH 的 `checkpoint_290000.pt` 只有 16MB(正常 217MB),已损坏;最后完整的是 `checkpoint_280000.pt`。
- 当时 `/inspire/hdd` 配额 82%(8.2T/10T),现在 1.9T 空闲。
- 结论:这两个是**存储写失败**,不是显存 OOM,可从各自最后的完整 checkpoint 续跑。

## 3. CUDA OOM 根因(full-covariance 多状态)

`fork-v2` 的报错在 `chunked_delta.py:81`:

```python
q_k_a = torch.tril(torch.einsum("bthk,bshk->bhts", query, a))
```

`chunked_branch.py:437` 以 `B*M` 维调用(`B=4, M=64` → 256),每 bank `[H=4, K=64]`,
`k_a` / `q_k_a` 各 `[256,4,256,256]` ≈ 268MB,**加上 `return_states=True` 与 full-covariance
几何因子 [256,4,64,64]**,整卡 79.06 GiB,超过 H100 的 79.18 GiB。

`bench-single-vs-addable` 的 `addable`(max_states=64)同样 OOM:
```
peak_allocated_gb: 65.1  (single 只有 37.5)
```

`m64-fix` 之所以能跑完,是因为它走 `run_pretrain_full_fix.sh` 的配置(含 `grad_checkpoint`),
把多状态的显存压了下来。

**结论:full-covariance × max_states=64 × chunk_len=256 × return_states 是显存杀手,
不是 bug,是当前实现的内存复杂度过高。**

## 4. MARCH 的 anchor_embed bug(已修复)

实际训练(小规模 pilot)用的 `new/fair_mqar/chunked_march.py:96`:

```python
self.anchor_embed = nn.Parameter(torch.randn(config.d_model) / ...)
...
a_hidden = self.anchor_embed.to(dtype).expand(...)   # 固定向量,不是内容
ak = self.anchor_k_proj(a_hidden)                     # κ = W_k · anchor_embed
```

即 anchor 路由 key 来自**一个学出来的固定 embedding**,不是论文的**内容路由** `κ = W_k u_m`。
这使所有 anchor 的 key 共享同一方向,路由退化,是 MARCH 小模型 loss 卡在 ~3 学不动的直接原因。

`new/fair_mqar_fix/chunked_march.py:284-287` 已修复为内容路由:

```python
a_hidden = local[:, end - 1 : end, :].to(dtype)   # chunk 末尾真实隐状态
ak = self.anchor_k_proj(a_hidden)                  # κ = W_k · u_m  ✓
```

## 5. Branch Memory 的路由是内容相关的(无此 bug)

`new/branch_memory/branch_memory/mixer.py:88-94` 的地址(路由 key):

```python
def descriptor(self, state):
    sig = einsum('bhvk,hpv->bhpk', state, self.value_probes)   # 真实内存内容
    sig = sig / sig.square().mean(-1).add(1e-6).sqrt()         # RMS 归一化
    return einsum('bhp,hpr->bhr', sig, self.content_proj)      # → 地址 r
```

`value_probes` / `content_proj` 是可学习参数,作用于真实状态内容,所以地址**随内容变化**,
不是固定向量。这是 branch 对 MARCH anchor-token 流的替代(mixer.py:69-70 注释明确写明)。
**Branch 没有 MARCH 那种固定向量的 bug。**

## 6. null_route bias = 1.0 疑点(建议先查)

`mixer.py:68,74`:

```python
self.null_route = nn.Linear(c.d_model, c.n_heads, bias=True)
nn.init.constant_(self.null_route.bias, 1.0)
```

地址 logits 初始 ~0,而 null logit 初始 = 1.0,即**模型一开始就倾向走 null(不读历史)**,
可能使记忆模块收不到有效梯度。这是最像"该学不该固定"的地方,能直接解释 loss 平台化。

## 7. 固定标量超参(不学习)

`tau=1.0, ridge=1.0, protect=8.0, fork_cost=0.02, protection_decay=0.95` 全部硬编码,
fork/replace 决策 `argmin` 是**不可微硬切换**(`math.py:138` `choice = costs.detach().argmin`)。

---

## 8. Cholesky 稳定性

`correction_full`(`math.py:45-80`)对非 SPD 几何直接 raise。几何
`H = ridge*I + protect*C`,`C` 由归一化 q 的外积累加并在 `update_protection` 显式对称化,
理论 SPD(ridge>0),但训练中若 `differentiate_covariance=True` 梯度流经 Cholesky,
数值退化可能导致发散。暂无直接崩溃证据,列为观察项。

## 11. 下一步建议(按优先级)

1. **查 null_route bias=1.0**(§6)—— 最像"固定值"坑,直接导致记忆读不出。
2. **降低 full-covariance 显存**(§3)—— 减小 max_states / chunk_len,或用对角几何,
   让多状态分支能在一张 H100 上跑。
3. **0.79B 正式版未开跑** —— `run_0p79b.sh march` 已用修好的内容路由代码,
   但仍需先解决 §1/§3 的显存与稳定性问题再提交。
4. **磁盘写失败** —— 现已恢复 1.9T 空闲,MARCH 可从 `checkpoint_280000.pt` 续跑。
